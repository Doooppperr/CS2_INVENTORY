# API 额度与容量

- Inventory Small：Inventory 独立限额为每分钟 20 次、每日 5,000 credits、每月 150,000 credits。Global 2/min 仅适用于没有独立额度行的端点；全局 Inventory 请求节流保持 18/min。
- 深度扫描基准为 7 次 SteamWebAPI 请求：normal 1、trading 3、mode1 1、parse1 2。真实扣费按参数通常为 2–3 credits；应用按每次 3 credits 保守记账，包含分页、重试和失败尝试。Steam 官方公开库存不计供应商 Inventory 用量。明确记录为零次尝试时记零，不回填七请求估算。
- 定时扫描每日两轮：北京时间 **08:00 深度 / 20:00 轻量**。沿用 `{日期}-R2` 与 `{日期}-R5` 槽键，发布当天不重复建轮；08:00 前不跨日补扫。正常情况下发现延迟约 12 小时加扫描耗时，并非完整覆盖保证。
- 轻量轮每目标调用一次单库存端点，使用 `parse=1`、`try_first_seven_days_blocked_items=1`、`no_cache=1`、`with_no_tradable=1`，保留交易保护物品检测。mode 1 可能回退普通库存；`tradeprotectedmaxdays` 是从供应商首次观察起计算的上界，不是 Steam 精确解锁时间。
- Worker 单任务领取明确排除 `daily_light`，轻量组才会领取该类型；扫描前重验订阅权益，单目标失败不阻塞组内其余任务。两个并发槽共享供应商请求节流。
- 每目标每日基础预算：`7×3 + 1×3 = 24 credits`。55 个目标约 1,320/天、40,920/31 天；100 个目标约 2,400/天、74,400/31 天。分页、重试、首次扫描和管理员任务另计；目标数不是平台硬限制，需随目标增长复核容量。
- 每日用量按北京时间零点统计。本地账期优先取最近成功 `/account/me` 中有效的 `subscriptionstart` / `subscriptionuntil`；缺失、格式异常或已失效时回退每月 25 日估算，并返回 `billing_period_source` 供界面标注。保留历史账本，不用供应商自然月 `month` 冒充订阅账期余额；本地余额不代表官方真实余额。
- 每日与账期限额、30,000/15,000 两级余额预警只用于观测，不停止扫描；供应商硬限额仍由上游执行。每用户 `monitor_limit` 是独立硬限制，管理员下调额度不删除历史数据。
- 定时批次仅覆盖至少有一个有效订阅者的目标；共享目标合并扫描。Profile 仅在首次添加及七天后刷新昵称时调用，使用独立于 Inventory 的额度。

## 2026-10-14 排查结论

9 月备份与当前供应商账号均为 Inventory Small，非错误更换 API。旧 Worker 的 `claim_next_job` 未排除 `daily_light`，使轻量任务先被深度路径领取；原先直接测试轻量组没有覆盖真实调度入口。六轮均走深度路径，基础用量从设计的每目标 36 变成约 126 credits/天。本次修复分流并降为两轮后，基础预算较该缺陷路径减少约 81%，供应商实际扣费与分页/重试另行核对。
